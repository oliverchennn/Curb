## Required comparison semantics

- One documented origin and mobility profile; every named destination has equal weight. All strategies evaluate the same immutable snapshot.
- At most 12 candidate projects, at most 4,096 subsets. Eligible candidates have known nonnegative integer-cent costs with source and status (`assumed`, `quoted`, `unknown`). Unknown costs are disclosed and excluded, never coerced to free. Budget and cost arithmetic must stay within safe integer bounds.
- Condition-first sorts severity descending, then lower cost, then stable code-unit ID. It scans that order and takes each affordable candidate; an unaffordable item does not prevent considering later cheaper ones. Disclose condition/cost assumptions and exact selected order.
- Exact search recomputes graph connectivity for every feasible repair set. Maximize the number of destinations newly reachable compared with the empty repair set. Tie-break by lower spend, fewer repairs, then lexicographic stable repair IDs. Optimality is only over the supplied bounded candidates and declared assumptions.
- The shared evaluator honors directed edges, all remaining blockers and unknown coverage. Clearing blockers on an unknown edge leaves it unknown. Evidence review status alone does not make an edge passable. Neither strategy edits source observations.
- Results include named per-destination outcomes and correct restored-ID/count relationships. An already reachable destination is not restored again. Include single-repair outcomes and the effect of removing each selected repair from its plan so UI explanations can distinguish individual benefit from dependency on companions.
- Expose actual feasible/evaluated subset counts and benchmark the chosen graph on the demo machine. Target under one second; reduce scenario size before adding infrastructure. No generic solver or provider dependency is required.

A separate worse-condition C costs four and restores one. Condition-first selects C; exact search selects A+B. Show actual outputs, assumptions and source evidence, never describe this case as observed Princeton conditions.

Domain checks cover empty candidate sets, zero budget (including genuinely zero-cost projects), no affordable repairs, unknown/invalid/overflowing costs, deterministic ties and input reordering, directionality, unknown/disconnected edges, two blockers on one edge, already reachable destinations, same-origin trips, stale revisions, input immutability and repeated evaluation.
