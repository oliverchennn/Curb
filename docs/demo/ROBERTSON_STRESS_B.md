ROBERTSON-STRESS-B/1 exercised the Windows production app at `1ff75a3467b5ccf7a2554ce53e1b46cafe457c90` with contract `curb-survey-v1`. ## Reproduce the normal run

Use the pinned source with the [HTTP stress script](../../scripts/curb/stress_http.ts). The recorded run used Node 24.12.0, npm 11.6.2 and Next.js 16.4.1. The locked install added 69 packages, and the production build and app typecheck passed. The standalone command checks the new script, which the app's TypeScript include rules omit.

```powershell
npm.cmd ci --no-audit --no-fund
npm.cmd run build
npm.cmd run typecheck
node node_modules/typescript/bin/tsc --ignoreConfig --noEmit --strict --skipLibCheck --esModuleInterop --types node --target es2022 --module esnext --moduleResolution bundler scripts/curb/stress_http.ts
node node_modules/next/dist/bin/next start --hostname 127.0.0.1 --port 3193
# In a second terminal from the same checkout
node --import tsx scripts/curb/stress_http.ts http://127.0.0.1:3193
```

The runner accepts an explicit HTTP origin at `127.0.0.1` and rejects redirects. It caps each run at 120 attempts, each request at 15 seconds, and concurrent batches at eight requests. A batch consists of one endpoint and uses the same canonical survey and $1,500 budget payload for both export formats. The two batches per width generated 78 of the 108 normal attempts. The remaining attempts covered selectors, error responses, cancellation and recovery, review attribution, and static media ranges.

Times are measured through receipt of the complete body, before report verification. The normal run took 6.8 s including client startup and checks. Windows reported a 134.8 MiB initial server working set, 343.0 MiB maximum over 76 samples, 347.7 MiB process peak and 329.5 MiB at the end. Client peak was 227.4 MiB. The host had 12 available logical CPUs and 27.7 GiB RAM with no imposed memory ceiling. This was a short single-host sample. It gives no sustained memory trend, hosted concurrency limit or throughput guarantee.

- Repeated GET and HTML matched byte for byte. Each HTML report had all five expected finding IDs and embedded photos matching their disk hashes. Repeated PDF exports had identical decoded page-stream hashes and the same five evidence headings. Raw PDF files had five distinct hashes in the normal run. The renderer leaves creation and modification timestamps to pdf-lib, whose metadata initialization uses the current time. The stability check covers decoded page content and evidence IDs. [Renderer](../../src/server/curb/surveyReport.ts).
- The default and explicit survey selectors passed. Unknown valid IDs returned 404. Empty, duplicate or extra query parameters and unsupported report formats returned 400. Malformed JSON and the wrong content type returned 400. Both fixed-length and streamed bodies one byte over 2 MiB returned 413. After one client cancellation during a partial upload, a new HTML request returned 200 in 19.3 ms. The cancelled request yielded no observed HTTP status.
- Both export formats rejected a priority-only edit with the original rationale and accepted the edited priority generated by the named-review helper. Subsequent survey GETs matched the saved survey. The SHA-256, size and modification-time inventory of the survey JSON and every file under the Robertson public media directory stayed unchanged throughout the probes. [Request handlers](../../src/server/curb/survey.ts), [review helper](../../src/features/curb/survey/presentation.ts).
- The first and last 32 bytes of the original MOV, normalized MP4, annotated MP4 and backup MP4 returned 206 with the correct Content-Range and bytes in all eight probes. This measured HTTP range serving on Windows.

## Missing photo and recovery

In ignored `.curb-local/stress-b/runtime`, I copied the built `.next` tree, `public`, the survey data directory, `package.json` and `next.config.mjs`. The copied runtime used the parent checkout's installed Next binary. I moved only its copy of `public/curb/surveys/robertson-hall/defect-05.jpg` out of the media directory and started the copied runtime on port 3194 with its working directory set to the copy. From the main task checkout I ran:

```powershell
node --import tsx scripts/curb/stress_http.ts http://127.0.0.1:3194 missing
# Restore the copied photo to its original location and verify its hash.
node --import tsx scripts/curb/stress_http.ts http://127.0.0.1:3194 restored
```

Before restoration both exports returned structured 500 `SURVEY_UNAVAILABLE` (76.3 ms HTML, 33.6 ms PDF). Both immediately recovered to 200 after restoring the photo with the same SHA-256, without restarting the process (47.1 ms HTML, 214.6 ms PDF). The two GETs in each run remained 200. Recovered HTML bytes and PDF page-stream hashes matched the normal run.

The dated receipts are under ignored `.curb-local/stress-b/`. Build, typecheck and HTTP checks passed on November 14, 2026. The unchanged full unit suite was outside this stress pass.
